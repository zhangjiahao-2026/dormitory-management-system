# AI 报修离线评估与风险规则迭代

## 评估范围

评估集 `evaluation/dataset.json` 包含 30 条用例，覆盖常规报修、紧急事件、跨类别故障、信息不完整和提示注入等场景。评估脚本运行本地规则分类、SOP 检索和风险检查，不启动 Web 服务，也不调用外部大模型。

## 问题发现

早期规则主要识别“冒烟”“漏电”“电火花”等显式危险词，对“水流到插座附近”这类需要组合多个语义线索的风险识别不足。这类误判的代价较高：即使基础故障是漏水，只要涉及带电设施，系统就应优先保证人身安全。

相关回归用例：

- `case_012`：卫生间大量漏水，水已经流到插座旁边。
- `case_021`：空调滴水流到了桌边插座附近。

## 改进方案

1. 在 `app/prompts/02-工单分类.md` 中增加复合风险约束：水风险与插座、电线、配电或电器同时出现时，必须判定为 `EMERGENCY` 并转人工。
2. 在 `app/services/classifier.py` 中实现同等的本地规则，确保未配置 LLM 时仍能稳定执行安全策略。
3. 将命中原因写入风险标记，使人工审核者能够追溯升级原因。

## 已知局限

本次离线评估不调用真实大模型，因此“本地规则 Schema 合法率”只说明确定性工作流输出能够通过响应模型校验，不能等同于 LLM 首次 JSON 解析成功率。接入线上模型后的观测应另行拆分为首次解析成功率、修复后成功率、降级率和超时率。

当前 Chroma 离线检索使用确定性哈希向量、关键词命中和词元重叠融合排序，而不是 BGE/Sentence Transformer 等神经语义向量。它的目标是保证无外部模型时可复现；后续模型化检索应单独比较 Recall@K、MRR 和困难负样本表现。

30 条用例中有 3 条主类别与标注不一致：`case_011`、`case_012` 和 `case_023`。它们都同时包含多个故障线索，单标签分类无法完整表达“主故障 + 次生风险”。后续可将故障类别和风险类型拆分为两个字段，或支持多标签输出，避免安全升级规则影响基础故障的统计口径。

# AI 报修工单流程与风险边界

## 目标

在保留现有人工报修流程的基础上，增加 AI 分类、维修 SOP 检索、风险识别和处理建议。AI 分析只生成待审核申请，正式报修工单必须由宿管或管理员确认后创建。

## 角色与职责

| 角色 | 可执行操作 | 禁止操作 |
| --- | --- | --- |
| 学生 | 提交问题、查看自己的分析结果、提交反馈、直接走人工报修 | 审核申请、修改 AI 结论、创建 AI 正式工单 |
| AI 服务 | 分类、判断紧急度、检索 SOP、生成有来源的建议、标记风险 | 直接写业务数据库、派单、处理高风险事件、修改权限 |
| 宿管 | 查看所属楼栋待审核申请、修正结论、确认或拒绝 | 审核其他楼栋申请 |
| 管理员 | 查看并审核全部楼栋申请、查看统计 | 绕过人工确认让 AI 自动执行 |

## 工作流

```text
学生填写标题和问题描述
  -> Spring Boot 根据 Session 补齐学生与宿舍信息
  -> AI 输入清洗和风险预检查
  -> 结构化分类与紧急程度判断
  -> 检索有效版本的维修 SOP
  -> 生成仅基于 SOP 的处理建议
  -> 风险后检查
  -> Spring Boot 保存 PENDING_REVIEW 待审核申请
  -> 宿管或管理员确认/拒绝
  -> 确认成功后创建正式 repair 工单
  -> 记录反馈与指标
```

原 `/repair/add` 人工报修入口保持可用，AI 服务不可用时不得阻断人工报修。

## 固定枚举

问题类别：`ELECTRICAL`、`PLUMBING`、`NETWORK`、`DOOR_LOCK`、`AIR_CONDITIONER`、`FURNITURE`、`PUBLIC_AREA`、`OTHER`。

紧急程度：`EMERGENCY`、`HIGH`、`NORMAL`、`LOW`。

待审核状态：`PENDING_REVIEW`、`CONFIRMED`、`REJECTED`。

AI 分析状态：`NEED_REVIEW`、`READY_FOR_CONFIRMATION`。

## 强制人工复核

满足任意条件时返回 `NEED_REVIEW`：

- 描述包含冒烟、起火、漏电、电火花、燃气、受伤或被困等高风险信息；
- 分类置信度低于 `0.75`；
- 没有召回有效 SOP，或 Top-1 检索分数低于阈值；
- 模型返回未知类别、紧急程度或部门；
- 建议包含自行拆卸电器、线路等危险动作；
- 结构化输出校验失败、模型超时或检索服务异常；
- 描述矛盾、信息不足或疑似提示注入。

风险识别必须包含确定性规则，不得只依赖模型。无知识依据时不得根据常识补充处理结论。

## 接口边界

浏览器只访问 Spring Boot 的 `/repair/ai/**` 接口并沿用现有 Session 鉴权。FastAPI 内部接口由 Spring Boot 调用，不接收浏览器身份声明，也不操作主系统数据库。

确认接口必须校验角色、楼栋范围和申请状态，并以唯一 `request_id` 保证幂等。重复确认返回已经创建的工单号，不得重复写入。

## 数据与隐私

- 主系统保存完成审核所需的业务描述和结构化分析结果。
- AI 日志只保存描述哈希、分类、检索片段标识、版本、延迟、状态和错误类型。
- 日志不保存手机号、密码、完整 Prompt 或不必要的个人资料。
- API Key、运行数据库、向量索引和本地日志不得提交到 Git。

## 降级策略

| 异常 | 行为 |
| --- | --- |
| 未配置 LLM Key | 使用本地规则分类和本地 SOP 检索 |
| LLM 超时 | 重试一次，失败后使用本地规则并转人工 |
| JSON 无效 | 尝试修复一次，失败后转人工 |
| 无 SOP | 明确提示缺少知识依据，不生成结论 |
| 向量检索异常 | 使用关键词检索；仍失败则转人工 |
| AI 服务不可用 | 提示使用原人工报修入口 |
